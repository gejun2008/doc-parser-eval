## 1. 「推理模型不该和 OCR 比」——这个质疑要换个提法才成立

表里六个系统，**没有一个是传统 OCR 流水线**：

| 系统 | 实际形态 |
|---|---|
| DeepSeek-OCR-2 | 端到端 VLM |
| MinerU2.5 | VLM + 版面流水线混合 |
| PaddleOCR-VL-1.5 | VLM（名字里有 OCR，架构不是） |
| Qwen3.5-35B-A3B | 通用多模态，无文档微调 |
| Gemini3.1-Pro | 前沿通用多模态 |
| Infinity-Parser2-Fin | 文档微调 VLM |

副标题写的是「vs. leading OCR/VLM models」，**但 OCR 那一半一个都没有**：
没有 Tesseract/ABBYY 这类传统引擎，更关键的是
**没有 Azure Document Intelligence、AWS Textract、Google Document AI 这三家商业文档服务**。

所以「用推理模型比 OCR」不是这张表的毛病——**它整张表都是推理模型内部的横评**，
任务口径（图像 → 结构化文本）是一致的，这一层没问题。

真正的毛病是另外三条：

1. **现状方案缺席。** 我们要替换的是 Azure DI，而它不在表里。
   这张表无论证明了什么，都没有对「该不该换掉 Azure DI」说过一个字。
   表里的对手集是「开源 VLM 解析器 + 两个通用大模型」——
   那是一家开源解析器厂商的竞争集，不是一家银行的采购候选集。
2. **数据集、评分脚本、对手分数三者都在厂商手里。** Financial Benchmark 没有公开定义，
   评分实现未公开，技术报告自承带 * 的基线由他们重跑（§1.4）。
   olmOCR-Bench 至少有公开榜单可交叉校验，这张表没有任何外部锚点。
3. **决定我们结论的那条轴根本没上表。** 置信度、确定性、bbox 来源、跨页状态、
   并发下的吞吐、SLA、版本锁定——Azure DI 赢或输都在这些项上，不在字符准确率上。
   准确率表格没有办法表达「temperature 0 下输出不可复现」（t0-findings.md §9），
   而那恰恰是银行最在意的。

## 2. 按他们自己的数读，结论对他们不利

### 2.1 93.56% 是这张表里他们最弱的差异化，却被挂在首页

与各对手在 Overall Char. Acc. 上的差距：

| 对手 | 差距 |
|---|---|
| MinerU2.5（**开源、可自建**） | **+1.33** |
| PaddleOCR-VL-1.5（开源） | +2.96 |
| DeepSeek-OCR-2（开源） | +3.54 |
| Gemini3.1-Pro（通用，已有商业采购路径） | +5.50 |

**整个 93.56% 相对最好的开源替代品的领先幅度是 1.33 个百分点。**
research-plan.md §3.1 要做的 GT 错误率抽检在这里的杀伤力最大：
**GT 自身只要错 2%，1.33 点的差距就完全落在噪声里。** 这是拆这张表最省力的一刀，
而且一刀下去，表里 Cell Acc 那一组 2.4–3.9 点的差距也跟着失去分辨率。

### 2.2 他们真正的优势是表格结构，而那一栏的绝对值最难看

相对领先幅度排序：

| 指标 | Fin | 次优 | 相对倍数 |
|---|---|---|---|
| Overall **Table** Acc. | 66.73 | 53.74 (MinerU2.5) | **1.24×** |
| Overall Page Acc. | 61.59 | 53.91 (MinerU2.5) | 1.14× |
| Overall Char. Acc. | 93.56 | 92.23 (MinerU2.5) | 1.01× |

**已测结论（基于厂商公开数字）**：他们的差异化集中在表格结构，不在字符识别。
但 Table Acc 的绝对值是 **66.73**——整张表准确率三分之一不到的失败率。

**工作假设（待验证）**：这个形状符合 VLM 微调的预期——
表格结构是生成格式问题，SFT/RL 能显著改善；字符准确率受视觉编码器上限约束，
而表里各家用的编码器规模相近，所以谁也拉不开。若成立，则含义是
**他们后续版本在字符准确率上的提升空间很小**，这一点对 POC 之后的路线图判断有用。

### 2.3 Overall Cell 94.19 与 Overall Table 66.73 之间的 27 点鸿沟

单元格大多对，整张表经常错。在金融场景这比明显崩掉更危险——
**它看起来是对的**。结合 bbox 是生成 token 这一点
（`docs/architecture-findings.md`），没有任何信号会提示这一页的表结构出了问题。

### 2.4 Page Acc 61.59 直接否掉 ROI 模型里的 99.7% 自动化率

在他们自己的数据、自己的评分、自己的最优模型上，**整页全对的比例是 61.59%**。
近四成页面至少含一处错误。银行流程的操作单位更接近「页」而不是「字符」。

**从 61.59% 的页准确率出发，任何不是「全量复核」的复核策略都到不了 99.7% 自动化率。**
research-plan.md §1.4 要求用我们自测的置信度数据去证伪 99.7%——
现在有了更省事的路径：**用他们自己首页上的另一个数字去证伪**。这一条进正文。

### 2.5 他们在扫描件上的优势几乎消失，而 HSBC 的难件都是扫描件

Text PDF → Scan PDF 的掉分幅度：

| 系统 | Text | Scan | 掉分 |
|---|---|---|---|
| Infinity-Parser2-Fin | 94.05 | 89.47 | **−4.58** |
| **Gemini3.1-Pro** | 88.10 | 87.79 | **−0.31** |
| DeepSeek-OCR-2 | 90.55 | 85.54 | −5.01 |
| MinerU2.5 | 92.71 | 88.15 | −4.56 |
| PaddleOCR-VL-1.5 | 90.98 | 87.39 | −3.59 |
| Qwen3.5-35B-A3B | 77.02 | 64.51 | −12.51 |

电子版上领先 Gemini **5.95** 点，扫描件上只剩 **1.68** 点。

**已测结论（基于厂商数字）**：他们的优势集中在电子原生文档——
恰恰是金融文档里最容易、最模板化的那一类。而 KYC 件、贸易融资单据、
往来函件这些真正难的文档族全是扫描件，**在那一侧他们和一个通用模型基本打平**。

这条直接回答了「通用多模态模型是否够用」：**按厂商自己的数据，在扫描件上够用。**

### 2.6 对手集的时间与阵容都停在半年前

对手发布日期从 2025-09 到 2026-02，主体是 2026-05。**用五月的模型比二月的基线。**
今天是 2026-09，表里最新的通用模型是 2026-02 的 Gemini3.1-Pro，
**GPT 系一个都没有**。

### 2.7 Financial Benchmark 只覆盖上市公司财报

分层只有 HK-Stock / MY-Stock / US-Stock。**没有 UK、没有 EU、没有 A 股**，
更没有 KYC、贸易融资、评级报告、往来函件。research-plan.md §3.3 的八个文档族里，
这张表大约只对应其中一个。HK 这一栏对 HSBC 有部分相关性，其余基本不适用。

## 3. 新发现：第三个变体 Infinity-Parser2-Fin，而我们不知道端点服的是哪个

| 变体 | 出处 | 权重 | 发布 |
|---|---|---|---|
| Infinity-Parser2-**Pro** | HF `infly/Infinity-Parser2-Pro` | Apache-2.0 公开 | 2026-06-08 |
| Infinity-Parser2-**Flash** | HF `infly/Infinity-Parser2-Flash` | Apache-2.0 公开 | 2026-06-08 |
| Infinity-Parser2-**Fin** | **仅见于擂台页** | **未见公开权重** | 2026-05-11 |

我们的端点只回显别名 `inf-mllm`，不含档位与版本号（t0-findings.md §3）。
现在这是个**三选一**的问题，三个分支的结论完全不同：

| 若端点是 | 则 |
|---|---|
| **Fin** | 93.56% 与我们测的是同一个模型，复现才有意义。但 Fin 的权重没公开，
「Apache-2.0 可自建」这条谈判杠杆对真正想买的模型**不成立**——这是 §1.4 的重大修正 |
| **Pro / Flash** | **93.56% 根本不适用于我们评测的模型**。首页数字与可购买的服务之间存在错配，
报告必须写明我们测的不是被宣传的那个 |
| Fin = Pro 的金融微调 | 需要厂商说清是同一权重加后处理，还是另一套权重 |

**动作**：`vendor-api.md` 未知项 #1 已从「Pro 还是 Flash」升级为三选一，并新增一问
「Fin 的权重是否开源；若否，93.56% 是否适用于我们拿到的端点」。
Flash 指纹比对（TASKS.md 的 GPU 例外项）现在只能证伪 Flash，**证不了 Fin**。

**顺带**：Fin 发布 2026-05-11 早于 Pro/Flash 的 2026-06-08。
§2.1 的泄漏时间切分用 2026-06-08，对 Fin 而言仍然是保守的（晚于其发布日），
**不需要调整**。但报告要说明切分点为何取 06-08。

## 4. 反证清单：要推翻「必须买他们的产品」，测什么

按性价比排序。前三条不做，报告就只是复述厂商的框架。

| # | 反证 | 打掉什么 | 成本 |
|---|---|---|---|
| **R1** | **在自建集上加两条缺席基线：Azure DI（现状）+ 一个前沿通用多模态（Gemini 3.1 Pro / GPT-6）** | 厂商表里最大的空白。若通用模型在我们的金融集上 cell acc 差距 < 3 点，「要不要买专用解析器」自动有答案 | 同批页面 ×2 条基线，都是 API 调用，符合「只测 API」约束 |
| **R2** | **GT 错误率抽检 50 条**（research-plan.md §3.1 已设计） | 1.33 点（vs MinerU）与 2.4–3.9 点（vs Gemini）的差距是否在噪声里。**一刀切掉整张表的分辨率** | 人工 0.5 人日 |
| **R3** | **同一批页面同时出「厂商口径 char acc」与「我们口径字段级准确率」** | §1.3 目前只是断言「字符准确率稀释关键字段」。两套数并排才是证据 | runner 加一个打分口径 |
| R4 | **扫描件族单独分层出数**，与电子原生族对比 | 验证 §2.5：优势是否只存在于电子版。这是 HSBC 场景相关性最高的一条 | 已在 §3.3 的扰动组设计内 |
| R5 | **页级准确率与字符级准确率同时报** | 验证「char 93 / page 61」的形状在我们数据上是否复现。若复现，99.7% 自动化率用他们自己的数被否掉 | runner 加页级判定 |
| R6 | **全量 3× 重复跑，出不一致率**（TASKS.md T8） | 93.56% 没有置信区间也没有重复次数说明。**问厂商：这个数跑了几次，取的哪一次** | 3× API 成本，约 3.4 小时（t0 §10） |
| R7 | **表格结构失败模式专项**：cell 对但 table 错的比例 | §2.3 的 27 点鸿沟在我们数据上的形状。这是他们唯一真优势的所在，也是最该压测的地方 | 断言设计已覆盖表格类 |
| R8 | **bbox 专项**：按 0–1000 还原后画回原图，抽检 IoU 与「文字对但框错」比例 | **olmOCR-Bench 与 Financial Benchmark 都不测 bbox**（architecture-findings.md 补充节）。纯生成模型在这一项上无人测量，而它是人工复核与定位取证的唯一依据 | 人工抽检，可与 R2 的 50 条合并做 |

### 反过来说：哪些情况下结论会支持他们

要保持独立性，证伪条件也要先写死：

- R1 里 Azure DI 在我们的金融集上明显落后，且差距集中在**表格结构**（对应 §2.2 他们的真优势）
- R4 里扫描件族上他们仍显著领先通用模型（即 §2.5 的结论在我们的数据上不复现）
- R2 的 GT 错误率 < 1%，差距不在噪声里
- R6 的不一致率低到不影响可审计性

**四条同时成立，则「表格密集的电子原生金融文档」这一族可替代成立**——
注意这个结论的范围有多窄，以及它和「93.56% 所以该买」相距多远。

## 5. 一句话版本

厂商的擂台没有作弊，它只是**在回答另一个问题**：
「在开源 VLM 解析器里我们是不是最好的」。答案大概是「是，主要靠表格结构」。

我们要回答的是「能不能替代 Azure DI，以及买专用解析器是否比用已有的通用多模态模型更划算」，
这两个问题的对手都不在他们表里，而他们表里的数字
（Page Acc 61.59、扫描件上对 Gemini 只剩 1.68 点、Char Acc 对开源只领先 1.33 点）
恰好是回答这两个问题时对他们最不利的证据。
