## 1. 结论

### 1.1 三个关键数字

**① 关键金额：Infinity 会静默丢掉整段表格，Azure 在同一批页上没有。**
在配对的 191 页上，Azure 的 486 条金额断言全部通过。Infinity 失败 12 条，p = 0.0005。
逐条对照原始输出后：
- 4 条只是减号字形不同，数值正确；
- **8 条是真实遗漏**，集中在 2 页。两页都是页首那段「上一页表格的续表」整段没输出，
  而调用状态是正常结束（`finish_reason=stop`），没有任何报错信号。

对全部 210 页的每个金额做全量扫描，又找到第 3 页：整张季度财务指标表（16 个金额）不见了。
三次重复调用，缺的完全一样。

**② 页面完整性：Infinity 通过得多，但这个差距还不能解读。**
正文锚点通过率：Infinity 91.3%，Azure 72.5%（99 : 15，p < 0.001）。
但这类断言对标点的全角/半角敏感，而判定器只归一了空白。
Azure 的 123 条失败还没有逐条裁定，**不能据此说 Azure 丢了内容**。

**③ 工程约束：没有置信度，并发加不上去，成本的盈亏平衡点可以算出来。**
- API 不返回置信度，请求 `logprobs` 会被静默忽略。
- 测试端点加并发不提高吞吐：并发 1 到 8，吞吐恒定在 1.6–1.8 页/分，超出部分是静默排队。
- 每页约 9.6k token。如果按 token 计费，只算输入 token 时，单价要低于约 **$1.13 / 百万 token**，
  才能与 Azure 牌价 $10 / 千页持平。

### 1.2 按文档类型的判断

| 文档类型 | 判断 | 证据 | 证据强度 |
|---|---|---|---|
| **港股年报、中报、招股书** | **可替代候选，进入 POC 验证** | 配对页上金额与科目归属断言两边都没有失败；页面完整性各族「未观察到显著差异」（p = 0.29 / 1.0 / 0.21） | 中：n = 171–210 条/族；但全量金额扫描尚未覆盖港股无小数的金额写法 |
| **A 股临时公告** | **可替代候选，进入 POC 验证** | 金额断言两边都没有失败；页面完整性 46 : 0，Infinity 通过更多 | 中：页面完整性差异未裁定 |
| **港股 KYC 类文件** | 本轮不下结论，可纳入 POC | 只有 39 条页面完整性断言，没有金额断言 | 弱 |
| **A 股年报、中报的财务报表与附注页** | **现阶段不可替代** | 3 页确定性遗漏整段金额，都出现在「页首是续表」的页上，且无报错信号。其中 2 页在配对集内，Azure 完整保留 | 中：机制明确、可复现。但 A 股年报配对页只有 13 页（Azure 19 页因网关超时失败，全在这一族），频率估计很粗 |
| **靠置信度决定哪些字段送人工复核的流程** | **不可替代（结构性）** | Infinity 不提供任何置信度，无法选择性复核，只能全量复核或抽检 | 强：API 行为实测 |
| **扫描件、倾斜件** | 本轮未与 Azure 对照 | Infinity 单边：倾斜 2° 的财报页三次调用都陷入无限复读，打满 32,768 token | 单边观察 |
| **贸易金融单证** | **未覆盖，现有结论不可外推** | 找不到合规的公开样本，五类来源的排除过程见 `corpus-method.md` | — |

### 1.3 POC 范围建议

1. **文档**：港股年报、中报、招股书，以及 A 股临时公告；只用原生电子版 PDF。
   A 股定期报告只作为**定向压力测试**，不进入替代范围（见第 3 条）。
2. **规模**：每个纳入的族至少 300 页含金额的页，按族分层出数，不合成总分。
   Infinity 与 Azure 跑同一批页，按页配对比较。
3. **定向集**：专门挑 **至少 50 页「页首是上一页表格续表」的页**，两边都跑，
   测静默遗漏的发生频率。本轮只找到 3 例，是否普遍要靠这组数据回答。
4. **强制护栏**（POC 期间就上，不是上线后再加）：
   - **全量金额对账**：对电子版 PDF，把输出里的金额与 PDF 文本层逐个比对。
     `tools/amount_scan.py` 就是这个检查的原型；港股的金额写法需要补上。
   - **监控 `finish_reason`**：`length` 一律判为调用失败、转人工，
     不能当作「解析质量差」静默放行。
   - **下游归一化**：把 U+2212「−」和全角「－」统一成 ASCII 减号。
     否则一个朴素的数字解析器可能丢掉负号，把负数读成正数。
5. **准入条件**（POC 开始前必须满足）：
   - 厂商书面答复 A1（被测模型与版本号，能否锁定版本）、A2（计费口径）、
     B1（能否提供置信度）、B3（生产吞吐与 SLA）；
   - 已发生泄漏的临时 key 完成轮换（C3）；
   - 如果贸易金融在业务范围内，由业务线提供样本页。

### 1.4 退出标准

出现以下任一情况，对应范围的 POC 即终止。阈值数字由业务方定，下面给的是建议起点。

| # | 条件 | 适用范围 |
|---|---|---|
| E1 | 配对页上，Infinity「有金额遗漏或替换的页」**显著多于** Azure（McNemar p < 0.05），且厂商在约定期限内无法修复 | 该文档族 |
| E2 | 定向续表集上，Infinity 遗漏页率 95% CI 的上界超过业务阈值（建议起点 1%） | A 股定期报告，以及任何含跨页表格的族 |
| E3 | 厂商不能提供**版本锁定**与**变更提前通知**。没有这两条，所有测试结论都可能被一次静默换模型作废 | 全部 |
| E4 | 用实际报价与 **HSBC 的 Azure 合同价**（不是牌价）重算后，每页有效成本高于 Azure。有效成本 = 调用成本 + 人工复核成本；没有置信度时，复核成本按全量复核或抽检计 | 全部 |
| E5 | 生产环境 SLA 给出的吞吐低于业务峰值需求 | 全部 |
| E6 | 复读退化（`finish_reason=length`）的页率超过阈值，或者厂商不承诺这类无效调用不计费 | 全部 |

## 2. 与 Azure DI 的配对对照

### 2.1 口径

- **只比双方都成功的页**。Azure 在 210 页里失败 19 页，**全部是 A 股年报**：
  16 页读超时，2 页提交结果未知，1 页网关失败。这些都是基础设施问题，不是识别错误，
  但它们让 A 股年报的配对页只剩 13 页。偏偏 Infinity 的失败模式就集中在这一类文档上。
- 两边用**同一版断言**判定，人工审核结果已回写进断言文件（GT）。
  `amount_label` 只计人工确认过的条目。
- 统计方法：McNemar 精确检验，b = 只有 Infinity 对，c = 只有 Azure 对。
  - p ≥ 0.05 写「未观察到显著差异」，**不写「持平」**；
  - 分层 n < 30 写「样本不足」；
  - 不合成加权总分。
- `unit_currency`（单位与币种声明）被公司侧**整类排除**，排除理由记为「空格匹配问题」。
  但判定器在比对前已经去掉了所有空白，这个理由对不上，需要核实。**本轮对单位/币种字段不下结论。**

### 2.2 按断言类型

| 类型 | n | Infinity 通过率 [95% CI] | Azure 通过率 [95% CI] | 只 Inf 对 : 只 Az 对 | p |
|---|---|---|---|---|---|
| `amount` 金额存在性与出现次数 | 486 | 97.5% [95.7, 98.6] | 100.0% [99.2, 100.0] | 0 : 12 | 0.0005 |
| `amount_label` 金额与科目同行 | 76 | 100.0% [95.2, 100.0] | 98.7% [92.9, 99.8] | 1 : 0 | 1.0，未观察到显著差异 |
| `page_integrity` 正文锚点完整性 | 448 | 91.3% [88.3, 93.6] | 72.5% [68.2, 76.5] | 99 : 15 | < 0.001 |

这张表的每一行都**不能直接当业务结论读**：`amount` 行要看 §2.3 的逐条裁定，`page_integrity` 行要看 §2.5。

### 2.3 关键字段失败逐条裁定

公司侧把关键错误率留空，理由原文是：字符串失败与仅靠距离判断的检查，都需要逐条做业务错误裁定，
不能直接算作已确认的关键错误。这个处理是对的。
Infinity 的原始输出在本机，13 条关键字段失败中属于 Infinity 的 12 条已逐条打开原始响应、
对照 PDF 文本层裁定。

| 失败 | 条数 | 页数 | 裁定 |
|---|---|---|---|
| 页首续表整段未输出 | 8 | 2 | **业务错误：静默遗漏** |
| 负数用了 U+2212「−」而不是 ASCII「-」 | 4 | 2 | 非业务错误，数值正确。但下游需要归一化（§1.3） |
| Azure：`label not found: 元（含税）` | 1 | 1 | **待裁定**。大概率是全角/半角括号的差异，需要在公司电脑看 Azure 原文 |

**两个遗漏样本**（详细记录见 `report-numbers-20260923.md`）：

- **A 股年报第 225 页。** 页首是上一页「应收账款按账龄披露」表的后四行：1 年以内、3 年以上、5 年以上、合计。
  Infinity 的输出直接从下一个小标题开始，这四行全部缺失。
- **A 股中报第 170 页。** 页首是上一页表格的「合计」行，含 4 个金额。Infinity 输出缺失这一行。

**裁定后的关键错误**（金额与科目归属两类，配对集）：

| | Infinity | Azure |
|---|---|---|
| 按断言计（n = 562） | 8 条，1.4% [0.7, 2.8] | 0 条已确认，1 条待裁定 |
| 按页计（n = 191） | **2 页，1.0% [0.3, 3.7]** | 0 页已确认，上限 2.0% |

**以页为单位读。** 8 条断言来自 2 次页级事件，彼此不独立。
按断言算出来的 8 : 0（p = 0.008）会夸大证据强度。
能确定的结论是：**这种失败模式存在、可复现、没有报错信号，并且 Azure 在同样的页上没有出现。**
它的发生频率，要靠 POC 的定向集来测（§1.3 第 3 条）。

### 2.4 全量金额扫描：抽样断言漏掉了什么

`amount` 断言每页只抽 4 个金额；`page_integrity` 的锚点又按设计排除了纯数字行。
所以「一整张数字表消失」这种失败，只有碰巧抽中那张表的金额时才会被抓到。

为此补了 `tools/amount_scan.py`：页上每个 A 股口径的金额（千分位加两位小数）都查一遍，
把文本层里的出现次数与模型输出里的出现次数对比。**目前只跑了 Infinity 一侧：**

| 项 | 值 |
|---|---|
| 含 A 股口径金额的页 | 73 页，金额共出现 2,149 次 |
| 缺失次数 | 27 次，1.3% [0.9, 1.8] |
| 有缺失的页 | **3 页，4.1% [1.4, 11.4]** |
| 三次重复调用的结果 | 缺失完全相同，是确定性失败 |

第 3 页是 A 股年报第 9 页：

- 整张「分季度主要财务指标」表缺失，包括 16 个金额：各季度营业收入、净利润、经营现金流；
- 这张表的标题还被挂到了上方那张续表的头上。
  读输出的人会以为「营业收入扣除」那张表就是分季度指标表。

抽样断言恰好只抽中了续表里的 4 个金额，全部通过，所以 §2.3 的失败明细里没有这一页。

**三页的共同点：页首都是上一页表格的续表，没有自己的表头。**
由此推测，模型把这种没有表头的页首片段当成了页眉区域；厂商 SDK 本来就默认丢弃页眉页脚（`sdk-findings.md`）。
**这是工作假设，没有坐实。**

**Azure 一侧的全量扫描要在公司电脑跑**，命令与拍照要求见 `docs/photo-numbers-prompt.md` 第二轮。
跑完之前，这一节只能算 Infinity 的单边结果。

### 2.5 `page_integrity` 的差距怎么读

Infinity 多通过 99 条，Azure 多通过 15 条，差距在统计上很显著。但是：

1. 锚点取自 PDF 文本层的原样字符。判定器只归一空白，不归一全角/半角标点。
   两家的 markdown 风格不同，标点习惯上的差异会直接变成失败。
2. Azure 的 123 条失败**没有逐条裁定**。它们到底是真的漏了内容，还是只是标点不同，现在不知道。
3. 差距主要集中在 A 股临时公告（46 : 0）。这类文档以正文为主，标点密度高。

**本轮只能写到这里**：在正文锚点完整性上，Infinity 的通过率显著更高，但这个差距里有多少是真实的内容差异，尚未裁定。
**不得写成「Azure 丢内容」。**
补救办法：在公司电脑从 Azure 失败里随机抽 20 条，人工归类，这是 1 小时量级的工作。

### 2.7 仍然存在的不对称

| # | 不对称 | 影响 |
|---|---|---|
| 1 | Azure 收到的是单页 PDF，保留了文本层；Infinity 收到的是 300 DPI 渲染图。Azure 是否利用了内嵌文本层，官方没有说明。**如果利用了，对 Azure 有利**，而且我们的 GT 本身就取自文本层 | 可能有利于 Azure |
| 2 | 两家的 markdown 风格各由厂商自己决定。判定器不归一标点，谁的标点习惯更接近文本层，谁就占便宜 | 方向不确定，见 §2.5 |

## 3. VLM 与 OCR 流水线的结构性差异

这一节不比分数，比**出错的方式**。
OCR 流水线认不出来时，会给低置信度或者留空；
VLM 认不出来时，可能生成一个格式完全正确的错误结果，或者干脆不输出，而调用状态照样是正常结束。
§2.3 和 §2.4 的遗漏，就是后一种的实例。

| 维度 | Infinity-Parser2（实测） | Azure DI |
|---|---|---|
| 置信度 | **没有**。`logprobs: true` 返回 200 不报错，但结果为 `null`，是静默忽略 | 逐 span 给 confidence |
| 确定性 | 同一页调用 3 次（`temperature 0`）：逐字一致 99.0%，断言结论翻转 0.17% [0.05, 0.63]。**金额类 562 条零翻转**，摇摆出在版面结构上，比如 `（2）`/`(2)` 和勾选框的写法 | 确定性流水线 |
| 静默失败 | 页首续表整段遗漏，`finish_reason=stop`（§2.3、§2.4） | 本轮配对集内未观察到 |
| 生成退化 | 2 次无限复读，打满 32,768 token：一次在密集数字表，一次在倾斜 2° 的财报页。重试 3 次结果都一样 | 不存在这种失败方式 |
| bbox | 由模型生成的坐标 token（0–1000 归一化），不是检测器测出来的 | 几何检测 |
| 版本可观测性 | 端点只回显别名 `inf-mllm`，`/v1/models` 返回 404，查不到档位和版本 | 有 API 版本号 |

**这笔交易的形状**：Infinity 用置信度、确定性、几何 bbox 这三样，换来了表格结构和正文完整性上的潜在优势。
在 HSBC 的场景里值不值，取决于下游是否依赖置信度做分流复核。
如果依赖，§1.2 已经给出判断；如果不依赖，就看 POC 里静默遗漏的频率。

**工作假设（未坐实）**：模型三次自称 Qwen3.5，与公开技术报告里的底座对得上。
但模型的自我描述不可靠，这一点不作为结论。

## 4. 服务与成本

### 4.1 延迟与吞吐

**所有数字只代表「当时的测量时段 + 并发条件 + 调用路径」，不代表生产能力，两列不做优劣比较。**

| | Infinity（测试端点，直连） | Azure DI（经公司网关） |
|---|---|---|
| 测量日期 | 2026-09-21 | 2026-09-22 |
| 并发 | 2 | 4 |
| 成功页 | 210 / 210 | 191 / 210（19 页基础设施失败） |
| 单页延迟 P50 / P95 | 22.5 s / 55.6 s | 17 s / 21 s（含网关与轮询，按整秒向下取整） |
| 整批耗时 | 46.5 min | 187 min（首末记录的时间跨度，含中断） |
| 限流行为 | 静默排队，没有 429 和 `retry-after`；并发 1→8 吞吐恒定 1.6–1.8 页/分 | 未测 |
| 吞吐的时段波动 | 不同日期实测 1.92 / 3.66 / 4.51 / 5.41 / 5.64 页/分，相差 2–3 倍 | 未测 |

对 Infinity 来说，按页数分档的延迟会退化成一个简单公式：**页数 × 单页延迟 ÷ 有效并发**。
测试端点的有效并发接近 1，所以一份 100 页的文档大约要 40–60 分钟。
生产环境是不是这样，从外部无法区分，这正是问题 B3 要问的。

### 4.2 Token 用量（实测，不依赖厂商）

| 项 | 金融集 210 页 |
|---|---|
| 输入 token / 页 | 中位 **8,868**。300 DPI 渲染后由像素数决定，与页面内容无关 |
| 输出 token / 页 | 中位 **984**，P95 1,782，最大 3,287 |
| 全批 | 输入 181.9 万 + 输出 20.2 万 = 202 万 token |
| 一次退化调用 | 输出 32,768 token，结果无效 |

### 4.3 成本：先给盈亏平衡价，不给结论

- **Azure DI Layout** 的牌价是 $10 / 千页，即每页 $0.01。**应以 HSBC 的实际合同价为准，需要找采购要。**
- **如果 Infinity 按 token 计费**：只算输入 token，单价要低于 $0.01 ÷ 8,868 ≈ **$1.13 / 百万 token** 才与牌价持平。
  再计入输出 token，门槛还会更低。
- **银行口径的成本** = 每页无关键错误的有效产出成本 + 人工复核成本。
  没有置信度，就不能只挑可疑字段复核。
  这一项直接决定厂商 ROI 模型里「99.7% 自动化率」能不能成立。

第一封信里问题 A2 只问了一句「怎么收费」，建议细化成能直接代入公式的六问：

1. 计费单位是按页、按 token、按调用，还是包年？
2. 如果按 token，**图像输入与文本输出的单价分别是多少**？
3. 撞到 token 上限的退化调用**收不收费**？一次就是约 3.3 万输出 token 的无效结果。
4. 输入分辨率由客户端决定，分辨率越低 token 越少。厂商推荐哪一档？降分辨率对准确率的影响由谁来承担？
5. 有没有阶梯价或承诺用量折扣？
6. 私有化部署怎么授权、怎么报价？权重本身是 Apache-2.0 开源的，采购买的到底是什么？

## 8. 方法透明度：我方犯过并修正的错

**报告的可信度来自评测过程可以被验证，不来自分数本身。**
下面每一处，如果没被发现，都会让数字失真，或者让数字看起来对、测的东西却是错的。

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| 1 | 禁止串是目标值的前缀 | `amount` 通过率假性显示为 **9.9%**，真实值是 97.9% | 禁止串必须不是目标值的子串 |
| 2 | 会重复出现的金额用了 `exactly_once` | 134 条注定会假失败 | 改为 `exactly_n`，期望次数取自文本层 |
| 3 | 页面锚点混进了纯数字行 | 8 条假失败 | 锚点至少要有 8 个文字字符 |
| 4 | 覆盖率直接比字符数 | 被 HTML 标记撑大到 1.82，被目录点线压低到 0.18 | 只数文字和数字 |
| 5 | 把中文「单位」当成计量单位 | 抓到「单位：<公司名>」，162 条里大部分报废 | 收紧正则，剩 111 条 |
| 6 | HKEX 日期参数写错 | 新旧两个时间窗口取到同一批文档 | 改用 `fromDate`/`toDate` |
| 7 | HKEX 没有翻页 | 老窗口假性 0 命中 | 按 `rowRange` 翻页 |
| 8 | 表格里折行的金额只抽到前半段 | 37 条断言成了必过的空心测试。**通过率恰好没变，但测的东西是错的** | 折行拼接 |
| 9 | 断言重新生成后审核 ID 会漂移 | 旧的审核结论可能被套到别的断言上 | 用审核指纹做版本校验，过期即拒绝 |
| 10 | 声称「Azure 可以利用全文上下文，对 Azure 有利」 | 不对称的方向写错了。网关实际传的是单页 PDF | 撤回，改写 §2.7 第 1 条 |
| 11 | 金额断言每页只抽样 4 个，页面锚点又排除了纯数字行 | **一整张 16 个金额的表消失，没被任何断言抓到** | 新增全量金额扫描 `amount_scan.py`，Azure 侧待跑 |

第 1 处如果没查就写进报告，结论会变成「该产品金额识别能力极差」，而真相是判定器写错了。
第 11 处恰好相反：它掩盖了 Infinity 的一个真实缺陷。
**异常值必须查到底再报，无论它对谁有利。**
