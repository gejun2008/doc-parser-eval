## 1. 结论

### 1.1 三个关键数字

**① 统一标点后，解析质量上没有一项指标 Infinity 显著好于 Azure。**
正文完整性 Azure 97.1%，Infinity 93.1%（只 Inf 对 : 只 Az 对 = 2 : 20，p = 0.0001）。
第一轮看到的「Infinity 91.3% 对 Azure 72.5%」，完全是因为 Azure 会把全角标点转成半角，
而判定器当时不归一标点。金额的抽样断言 Azure 100%，Infinity 97.5%。
单位币种、金额科目归属两项未观察到显著差异。

**② 两边都有丢金额的情况，但 Infinity 的已查实是整段丢表。**
在配对的 54 页 A 股金额页上做全量金额扫描：Infinity 缺 11 次（2 页），Azure 缺 6 次（2 页），
页级比较未观察到显著差异。Infinity 这 2 页已逐页核实：页首的续表整段没有输出，
调用状态照常是正常结束（`finish_reason=stop`），三次重复调用结果完全一样。
Azure 那 6 次还没查清原因。另有一页 Infinity 丢了一整张 16 个金额的表，
但 Azure 在该页调用失败，这一页没法对比。

**③ 工程约束：没有置信度，加并发没用，成本盈亏点可以算。**
API 不返回置信度，请求 `logprobs` 会被静默忽略。测试端点从并发 1 加到 8，吞吐一直是 1.6–1.8 页/分。
每页约 9.6k token；如果按 token 计费，只算输入时单价要低于 **$1.13 / 百万 token**，才能与 Azure 牌价 $10 / 千页持平。

**这三点合在一起**：替代的理由**不能来自解析质量**，本轮测到的质量指标 Azure 都持平或更好。
理由只能来自成本（要等厂商报价，A2）、部署方式（开源权重可以私有化部署），或其他业务考量。

### 1.2 按文档类型的判断

| 文档类型 | 判断 | 证据 | 证据强度 |
|---|---|---|---|
| **Word / Excel / PPT / HTML 原生文件** | **不能直接替代** | Infinity 只接受 PDF 和图片（SDK `utils/file.py` 里的格式白名单）；Office 文件要先转成 PDF 或图片，原生的文字和结构会丢失。Azure 可以直接处理 Office 和 HTML | 强：源码核实 |
| **港股年报、中报、招股书** | **关键字段未见差异，可以进 POC** | 金额、科目归属断言两边都没有失败；单位币种未观察到显著差异。正文完整性总体是 Azure 更好，分族结果待第三轮 | 中 |
| **A 股临时公告** | **关键字段未见差异，可以进 POC** | 金额断言两边都没有失败。第一轮里 Infinity 46 : 0 的领先是标点造成的，分族宽松结果待第三轮 | 中 |
| **港股 KYC 类文件** | 本轮不下结论 | 只有 39 条正文完整性断言，没有金额断言 | 弱 |
| **A 股年报、中报的财务报表与附注页** | **现阶段不能直接替代** | Infinity 有 3 页确定性的整段丢表（其中一页整张表 16 个金额），没有任何报错信号。Azure 在配对页上也有 2 页缺了 6 次金额，原因待查，所以**不能说 Azure 在这类页上没有问题** | 中：Infinity 的机制已查实、可复现；两边的频率都要靠定向测试 |
| **要按置信度决定哪些字段送人工复核的流程** | **不能替代（结构性原因）** | Infinity 不提供任何置信度，没法有选择地复核 | 强：API 实测 |
| **扫描件、倾斜件** | 本轮没和 Azure 对照 | 只测了 Infinity：页面倾斜 2° 时陷入无限复读，打满 32,768 token | 单边观察 |
| **贸易金融单证** | **未覆盖，现有结论不能外推** | 找不到合规的公开样本，见 `corpus-method.md` | — |

### 1.3 POC 范围建议

0. **先决条件：有替代的动因。** 质量上没有替代理由（§1.1），所以启动 POC 前，要么厂商报价显示有成本优势，
   要么业务上确实需要私有化部署，要么有其他明确的业务理由。三者都不满足时，不建议投入 POC。
1. **文档**：港股年报、中报、招股书，加上 A 股临时公告；只用原生电子版 PDF。
   A 股定期报告只做**定向压力测试**（见第 3 条），不纳入替代范围。
2. **规模**：每个纳入的族至少 300 页含金额的页，按族分层出数，不合成总分。两边跑同一批页、按页配对比较。
3. **定向集**：挑**至少 50 页「页首是上一页续表」的页**，两边都跑，比较整段遗漏的频率。
4. **强制护栏**（POC 阶段就要加上）：
   - **全量金额对账**：电子版 PDF 的输出金额逐个与文本层比对，原型见 `tools/amount_scan.py`，需要补上港股的金额写法。
   - **`finish_reason` 监控**：`length` 一律判为调用失败、转人工。
   - **下游归一化**：U+2212「−」统一成 ASCII 减号；全角/半角标点统一处理。两家的标点习惯不一样，这一点在第二轮已经实测确认。
5. **准入条件**：厂商书面答复 A1（被测模型与版本锁定）、A2（计费口径）、B1（置信度）、B3（生产吞吐与 SLA）；
   泄漏的临时 key 完成轮换（C3）；如果贸易金融单证在范围内，由业务线提供样本页。

### 1.4 退出标准

任一条触发，对应范围的 POC 就终止。阈值由业务方定，下面给的是建议起点。

| # | 条件 | 适用范围 |
|---|---|---|
| E1 | 配对页上，Infinity「有金额遗漏或替换的页」**显著多于** Azure（McNemar p < 0.05），且厂商无法在约定期限内修复 | 该文档族 |
| E2 | 定向续表集上，Infinity 遗漏页率的 95% CI 上界超过业务阈值（建议起点 1%） | A 股定期报告，以及所有含跨页表格的族 |
| E3 | 厂商不能提供**版本锁定**和**变更提前通知** | 全部 |
| E4 | 按实际报价与 **HSBC 的 Azure 合同价**（不用牌价）重算后，每页有效成本高于 Azure。有效成本 = 调用成本 + 人工复核成本；没有置信度，复核成本按全量复核或抽检计 | 全部 |
| E5 | 生产 SLA 给出的吞吐低于业务峰值需求 | 全部 |
| E6 | 复读退化（`finish_reason=length`）的页率超过阈值，或厂商不承诺这类无效调用不计费 | 全部 |

## 2. 与 Azure DI 的配对对照

### 2.1 口径

- **只比双方都成功的页。** Azure 在 210 页里失败了 19 页，**全部是 A 股年报**：16 页读超时、2 页提交结果未知、1 页网关失败。
  这些都是基础设施问题，不是识别错误，但因此 A 股年报的配对页只剩 13 页，
  而 Infinity 的失败模式恰好集中在这一类。
- 两边用**同一版断言**判定，人工审核结果已经回写到断言文件（GT）。`amount_label` 只算人工确认过的条目。
  参照是什么、判定规则、测不到什么（**断言不含坐标，本报告不评估版面定位能力**），以及如何自己复核任意一个数字，见**附录 C**。
- **两种判定口径并列。** 严格：只去掉空白，是 `check.py` 的原口径。宽松：再把全角转半角、删掉所有标点符号。
  金额类断言只用严格口径，因为逗号和小数点是数值的一部分。
  `page_integrity` 和 `unit_currency` 以**宽松口径为准**：两家的标点习惯不同，这是输出风格问题，不是内容问题（§2.5）。
- 统计：McNemar 精确检验，b = 只有 Infinity 对，c = 只有 Azure 对。p ≥ 0.05 写「未观察到显著差异」，
  **不写「持平」**；分层 n < 30 写「样本不足」；不合成加权总分。
- **更正**：第一轮公司侧汇总时，把 `unit_currency` 整类排除了，理由写的是「空格匹配问题」。第二轮核实发现：
  仓库里没有这条排除代码，是 AI 助手写表时自己决定的，理由也不对，真实原因是标点。
  这一类现在已经恢复进对照。

### 2.3 关键字段失败逐条裁定

Infinity 那 12 条金额失败，已经逐条打开原始响应、对照 PDF 文本层核实过。
Azure 那 1 条，第二轮摘出了原文。

| 失败 | 条数 | 页数 | 裁定 |
|---|---|---|---|
| Infinity：页首续表整段没有输出 | 8 | 2 | **业务错误：静默遗漏** |
| Infinity：负数用了 U+2212「−」，不是 ASCII「-」 | 4 | 2 | 非业务错误，数值正确 |
| Azure：`label not found: 元（含税）`。Azure 原文是 `元(含税)`，全角括号被转成了半角 | 1 | 1 | 非业务错误，标点字形差异 |

两个遗漏的样本：
- **A 股年报 p225**：页首是上一页「应收账款按账龄披露」表的后四行，Infinity 的输出直接从下一个小标题开始。
- **A 股中报 p170**：页首是上一页表格的「合计」行，Infinity 没有输出。

**金额和科目归属两类断言**（n = 562），裁定后的关键错误：Infinity 8 条，占 1.4% [0.7, 2.8]，集中在 2 页；Azure 0 条。
这 8 条是 2 次页级事件，彼此不独立，**应该按页来读**。
另外，全量扫描发现 Azure 也有缺失（§2.4），所以「Azure 0 条」只代表抽样断言覆盖到的那部分。

### 2.4 全量金额扫描：两边都查

`amount` 断言每页只抽 4 个金额，`page_integrity` 的锚点又排除了纯数字行，
所以「一整张数字表消失」只有碰巧被抽中时才抓得到。
`tools/amount_scan.py` 把页上每个 A 股写法的金额（千分位加两位小数）都查一遍，比对文本层和输出里各出现几次。

**配对集（第二轮，两边同一套规则）**：

| 项 | Infinity | Azure DI |
|---|---|---|
| 配对页 / 金额出现次数 | 54 页 / 1,544 次 | 同左 |
| 缺失次数 | 11 次，0.7% [0.4, 1.3] | 6 次，0.4% [0.2, 0.8] |
| 有缺失的页 | 2 页（p225、p170） | 2 页（p170、p202） |
| 缺失的性质 | **已核实**：页首续表整段丢失 | **待查**（第三轮） |

按页比：只有 Infinity 缺 1 页，只有 Azure 缺 1 页，两边都缺 1 页，**未观察到显著差异**。
p170 上两边都缺 4 次，但 Azure 的抽样断言在这一页全部通过，也就是说 Azure 缺的是**另外 4 个金额**。
缺了哪几个，要等第三轮 `--show-missing` 的输出。

**配对集以外（只有 Infinity 的结果）**：A 股年报 p9，**整张「分季度主要财务指标」表（16 个金额）没有输出**，
表题还被挂到了上面那张续表的头上。Azure 在这一页因网关超时失败，所以没法比较。
Infinity 在全部 210 页上：73 页有金额，缺 27 次，涉及 3 页；三次重复调用结果完全一样。

**Infinity 这 3 页的共同点**：页首都是上一页表格的续表，没有自己的表头。
推测模型把这种片段当成了页眉区域，而 SDK 默认会丢弃页眉页脚。**这是工作假设，未经证实。**

### 2.5 正文完整性：第一轮的差距是标点造成的

第一轮严格口径下，Infinity 多对 99 条，Azure 多对 15 条。当时已标注「不能读成 Azure 丢内容」。
第二轮用宽松口径重判：

- **Azure 会把全角标点转成半角。** 原文摘录可以直接证明（`（含税），` → `(含税),`）；
  `unit_currency` 严格口径下 Azure 只过了 2/93，也是同一个原因（`单位：元` → `单位:元`）。
- 标点统一后结果反过来了：**Azure 97.1%，Infinity 93.1%，2 : 20，p = 0.0001**。
- 宽松口径下仍然失败的是「真实缺失候选」：Infinity 31 条，Azure 13 条。还要抽样人工确认。

**读法**：在正文完整性上，Azure 显著好于 Infinity。
Azure 不保留全角标点的字形，这是格式差异，下游做归一化就能解决，不算内容错误。

### 2.6 按文档族、按时间窗口

第一轮的分族、分窗口表是**严格口径**，并且把三类断言混在一起。「只 Inf 对」的 100 条里有 99 条来自 `page_integrity`，
而第二轮已经证明这部分主要是标点差异。**所以第一轮分族表里 Infinity 的领先不成立**，原表保留在
`report-numbers-20260923.md`，只作为记录。

宽松口径的分族结果要等第三轮（`relaxed_recheck.py --by-family`）。在那之前，分族只能看金额类断言：
全部 Infinity 金额失败都出在 A 股年报、中报；港股各族和 A 股公告两边都没有金额失败。

## 3. VLM 与 OCR 流水线的结构性差异

这一节不比分数，比**出错的方式**。
OCR 流水线认不出来时，会给低置信度或者留空；
VLM 认不出来时，可能生成一个格式完全正确的错误结果，或者干脆不输出，而调用状态照样是正常结束。
§2.3 和 §2.4 的遗漏，就是后一种的实例。

| 维度 | Infinity-Parser2（实测） | Azure DI |
|---|---|---|
| 置信度 | **没有**。`logprobs: true` 返回 200 不报错，但结果为 `null`，是静默忽略 | 逐 span 给 confidence |
| 确定性 | 同一页调用 3 次（`temperature 0`）：逐字一致 99.0%，断言结论翻转 0.17% [0.05, 0.63]。**金额类 562 条零翻转**，摇摆出在版面结构上，比如 `（2）`/`(2)` 和勾选框的写法 | 确定性流水线 |
| 静默失败 | 页首续表整段遗漏，`finish_reason=stop`（§2.3、§2.4），已查实 | 配对集内 2 页缺 6 次金额，性质待查；Azure 有置信度可以辅助发现 |
| 标点字形 | 保留原文的全角标点 | **全角标点转成半角**（第二轮实测），下游需要归一化 |
| 生成退化 | 2 次无限复读，打满 32,768 token：一次在密集数字表，一次在倾斜 2° 的财报页。重试 3 次结果都一样 | 不存在这种失败方式 |
| bbox | 由模型生成的坐标 token（0–1000 归一化），不是检测器测出来的 | 几何检测 |
| 版本可观测性 | 端点只回显别名 `inf-mllm`，`/v1/models` 返回 404，查不到档位和版本 | 有 API 版本号 |

**这笔交易的形状**：Infinity 放弃了置信度、确定性和几何 bbox。
第一轮我们以为它换来了正文完整性上的优势，第二轮统一标点后，这个优势不存在了（§2.5）。
本轮数据里，**看不到它用这三样换来了什么解析质量上的回报**。
它可能的价值在解析质量以外：开源权重可以私有化部署，以及成本（要等报价）。

**工作假设（未坐实）**：模型三次自称 Qwen3.5，与公开技术报告里的底座对得上。
但模型的自我描述不可靠，这一点不作为结论。

## 4. 服务与成本

### 4.1 延迟与吞吐

**所有数字只代表「当时的测量时段 + 并发条件 + 调用路径」，不代表生产能力，两列不做优劣比较。**

| | Infinity（测试端点，直连） | Azure DI（经公司网关） |
|---|---|---|
| 测量日期 | 2026-09-21 | 2026-09-22 |
| 并发 | 2 | 4 |
| 成功页 | 210 / 210 | 191 / 210（19 页基础设施失败） |
| 单页延迟 P50 / P95 | 22.5 s / 55.6 s | 17 s / 21 s（含网关与轮询，按整秒向下取整） |
| 整批耗时 | 46.5 min | 187 min（首末记录的时间跨度，含中断） |
| 限流行为 | 静默排队，没有 429 和 `retry-after`；并发 1→8 吞吐恒定 1.6–1.8 页/分 | 未测 |

测试端点的有效并发接近 1，所以一份 100 页的文档大约要 40–60 分钟。
生产环境是不是这样，从外部无法区分，这正是问题 B3 要问的。

### 4.3 成本：先给盈亏平衡价，不给结论

- **Azure DI Layout** 的牌价是 $10 / 千页，即每页 $0.01。**应以 HSBC 的实际合同价为准，需要找采购要。**
- **如果 Infinity 按 token 计费**：只算输入 token，单价要低于 $0.01 ÷ 8,868 ≈ **$1.13 / 百万 token** 才与牌价持平。
  再计入输出 token，门槛还会更低。
- **银行口径的成本** = 每页无关键错误的有效产出成本 + 人工复核成本。
  没有置信度，就不能只挑可疑字段复核。
  这一项直接决定厂商 ROI 模型里「99.7% 自动化率」能不能成立。

第一封信里问题 A2 只问了一句「怎么收费」，建议细化成能直接代入公式的六问：

1. 计费单位是按页、按 token、按调用，还是包年？
2. 如果按 token，**图像输入与文本输出的单价分别是多少**？
3. 撞到 token 上限的退化调用**收不收费**？一次就是约 3.3 万输出 token 的无效结果。
4. 输入分辨率由客户端决定，分辨率越低 token 越少。厂商推荐哪一档？降分辨率对准确率的影响由谁来承担？
5. 有没有阶梯价或承诺用量折扣？
6. 私有化部署怎么授权、怎么报价？权重本身是 Apache-2.0 开源的，采购买的到底是什么？

## 附录 C 评测方法：参照是什么、怎么判、测不到什么

本附录回答一个问题：**报告里的每个通过率，是拿什么当标准答案、按什么规则判出来的。**
这里的每一项都可以对照仓库里的文件和代码自行核对，不需要相信我方的转述。

### C.1 对比流程

1. 两个系统处理**同一批 210 页**。选页规则是确定性的，没有随机性（`docs/corpus-method.md`）；
   语料来源 URL 和 sha256 在 `data/corpus/manifest.csv`。
2. 两边各自输出 markdown，**我方不做任何格式转换**。Azure 调用时带 `outputContentFormat=markdown`，
   直接取 `analyzeResult.content`，由微软自己决定版面怎么转成 markdown。每页原始记录里都写了
   `"conversion_by_us": false`（`tools/azure_di_runner.py`）。这样做是为了避免转换规则变成影响对手分数的变量。
3. `tools/check.py` 用**同一套断言文件**分别判定两边输出，每条断言得出通过或失败，并记下失败原因，
   写入各自 run 目录的 `results.csv`。
4. `tools/compare_systems.py` 把两边在**同一条断言**上的结果配对，做 McNemar 检验：
   只看「只有 Infinity 对」(b) 和「只有 Azure 对」(c) 的条数，两边都错的算共同难度，不计入差异。

### C.2 参照（GT）是什么

参照**不是整页的标准 markdown**，而是逐条的**断言**：「第 N 页的输出里，某个字符串必须出现、
出现几次、哪些错误写法不能出现」。每份文档一个 YAML，共 53 份，放在 `data/assertions/<doc_id>.yaml`，入库。

之所以不做全文标准答案：一份年报的全文 GT 要花好几人日，而且会把评测稀释成又一次单页 OCR 测试。
断言法沿用 olmOCR-bench 的 pass/fail 思路（`docs/assertions.md`）。

一条真实断言（报告 §2.3 中 Infinity 失败的那条）：

```yaml
- id: a_share_annual_old_002310_2026-04-30_p225_am01
  type: amount
  severity: critical
  page: 225
  eval_on: md
  rule: exactly_n
  n: 2                       # 文本层里这个金额出现 2 次（本期、上期两栏）
  target: 23,364,600.49
  forbid:                    # 小数点错位、丢千分位，这两种写法不得出现
  - 23,364,60.049
  - '23364600.49'
  status: auto_textlayer
```

**断言的来源分三层，只有一层是纯人工的**：

| status | 条数 | GT 从哪来 | 人工参与 |
|---|---|---|---|
| `auto`：`page_integrity` 正文锚点 | 480 | PDF 文本层中全文唯一、≥ 12 字符、≥ 8 个文字字符的片段 | 无。字符本来就取自原文，只用于查漏页和幻觉 |
| `auto_textlayer`：`amount`、`unit_currency` | 673 | PDF 文本层 | 抽样审计 53 条金额，改值 1 条，GT 错误率估计 1.9% [0.3, 9.9] |
| `draft` → `confirmed`：`amount_label` 科目归属 | 76 | 脚本给出候选，人工对照渲染页图逐条确认 | 全部人工。确认 76 条，驳回 0 条，改值 1 条 |

合计 1,229 条。人工审核结果见 `report-numbers-20260923.md` 表 4。

**为什么科目归属必须人工**：PDF 文本层对「这串字符在不在这一页」是可靠的，但对**顺序和归属**不可靠。
跨列拼接可能把隔壁列的标签配给金额，所以脚本给出的标签只能当候选。
`check.py` 只执行 `auto`、`auto_textlayer`、`confirmed` 三种状态，**`draft` 状态的断言不参与判定**
（第 166 行；`--include-draft` 只供调试，结果不进报告）。

### C.3 判定规则

全部是**纯文本规则**，在归一化后的输出文本上做子串计数（`tools/check.py` 中的 `judge()`）：

| 规则 | 含义 |
|---|---|
| `exactly_once` | 目标串恰好出现 1 次 |
| `exactly_n` | 恰好出现 n 次，n 取自文本层的实际出现次数 |
| `forbid` | 列出的错误写法一条都不能出现。禁止串必须不是目标值的子串，否则会造成假失败（§8 第 1 条） |
| `label_proximity` | 金额与其科目标签都在输出里，并且两者之间的字符距离 ≤ 120 |

归一化分两种口径（§2.1）：**严格**只去掉空白；**宽松**再做全角转半角并删掉标点。金额类只用严格口径。

### C.4 这套方法测不到什么

**断言里没有坐标。** 断言 YAML 和人工审核导出的 JSON 都只定位到**页码**，不含 bbox 或 polygon。
这决定了本报告的适用范围：

- **只测了文字和金额是否正确、完整，没有测版面定位能力。**
  Azure 返回的 `boundingRegions` 和 Infinity 的 bbox 输出都没有参与评分。
  如果下游需要坐标（例如在原文上高亮溯源、复核时跳到原文位置），**这一项目前没有证据，任何一方都不能据本报告下结论。**
- **科目归属用文本距离近似**（≤ 120 字符），而不是用版面上是否同一行来判定，是一个较弱的代理指标。
  两个系统的表格 markdown 写法不同，这个距离对两边未必完全公平。
- **GT 取自 PDF 文本层**，而 Azure 收到的是带文本层的 PDF，Infinity 收到的是渲染图。
  如果 Azure 利用了内嵌文本层，这一点对 Azure 有利（§2.7 第 1 条）。
- 断言是抽样：金额每页只抽 4 个，所以另外用全量金额扫描补了一道（§2.4）。

如果要补测坐标：可以从 PDF 文本层取每个金额的 bbox 作为 GT，与两边返回的坐标算 IoU。
这需要新增一类断言，不在本轮范围内。

### C.5 如何自己复核任意一个数字

以 §2.3 中 Infinity 的第一条金额失败为例，从断言追溯到原始响应：

| 步骤 | 文件 | 看到什么 |
|---|---|---|
| 1. 断言 | `data/assertions/a_share_annual_old_002310_2026-04-30.yaml`，id `…_p225_am01` | 要求 `23,364,600.49` 出现 2 次 |
| 2. 原文 | `data/corpus/manifest.csv` 中该文档的 `source_url`（巨潮资讯网公开年报），第 225 页 | 本期、上期两栏各有一次 |
| 3. 模型原始响应 | `runs/inf-mllm_doc2md_20260921T013924Z/raw/…_002310_2026-04-30_p225.json` | HTTP 状态、响应头、`usage`、`finish_reason`、UTC 时间戳、服务端回显的 `model`，以及原始输出全文 |
| 4. 判定结果 | 同一 run 目录下的 `results.csv` | `pass=0`，原因 `expected 2, found 1` |
| 5. 重跑判定 | `python tools/check.py runs/inf-mllm_doc2md_20260921T013924Z` | 不调用 API，只用落盘的原始响应，结果应该完全一样 |

报告里的任意一条通过或失败，都可以按这五步复核。

### C.6 可追溯性的现状（如实声明）

- 人工审核是在公司电脑上做的，审核结果回写到了**公司电脑上的**断言文件。
  **本机仓库里这 76 条科目归属断言目前仍是 `draft`**，审核导出文件 `review_all.json` 尚未带回入库。
  在补齐之前，别人在本机仓库重跑 `check.py`，`amount_label` 会被跳过，复现不出 §2.2 的这一行。
  补救：把 `review_all.json` 带回，执行 `python tools/apply_review.py review_all.json`，
  然后把导出文件和更新后的 YAML 一起入库。
- Azure 侧的数字是在公司电脑上算出、以拍照转录的方式带回的（`report-numbers-20260923.md`，每张表带校验和）。
  Azure 的原始响应不在本机，这一侧的逐条复核要到公司电脑上做。
