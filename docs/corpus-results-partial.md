### 一个典型错误：O2O → 020

`a_share_annual_old_300572` 第 18 页，原文「以车辆检测为核心的 O2O 服务模式」，
输出为「…020服务模式」——字母 O 被读成数字 0。

这类字符混淆在通用 OCR 指标里是小数点后的噪声，在金融场景里可能直接影响
账号、代码、编号字段。**这正是 research-plan.md §2.3 要求指标对齐业务后果的理由。**

## 内容覆盖率：中位 0.98

逐页比对「输出的文字与数字字符数 / PDF 文本层的文字与数字字符数」：

|---|---|

| 最低 | 0.71 |
| < 0.95 | 34 页（16.6%） |
| < 0.9 | 8 页（3.9%） |
| < 0.5 | 0 页 |

**已测结论**：没有整页丢失的情况，损失是局部的、几个百分点量级。
按族的中位覆盖率在 0.96–1.00 之间，无明显差异。

**口径说明（两次算错的教训）**：
1. 直接比字符数会被 HTML 表格标记撑大（`<table><tr><td>` 都算字符），
   首次算出中位 1.82，是假象。必须剥掉标记。
2. 剥标记后仍要只数文字与数字：年报目录页的文本层含大量点线（`......`），
   模型正确地没有输出它们，按全字符算会得出 0.18 的假性「漏读」。

两次都修正后才是上表的数字。**报告附录要写明这个口径**，
否则别人用不同算法会得到完全不同的覆盖率。

## T2 扰动组：衰减不显著，但旋转触发了复读退化

run_id `inf-mllm_doc2md_20260921T031242Z`，2026-09-21 03:12–04:09 UTC，
42 页（每族 6 页，固定 seed）× 5 种扰动 = 210 次调用，图片输入。
口径见 `tools/perturb.py`：降源 PDF 的 DPI 会被 300 DPI 重栅格化抵消，
必须以图片送入才测得到真实低分辨率（sdk-findings.md §6）。

**对照组是原始 run 中同样这 42 页的同样 100 条断言**，不是全量 480 条。
拿 100 条去和 480 条比是错的。

|---|---|---|---|---|
| **原始 300 DPI（对照）** | 94/100 | **94.0%** | — | [0.875, 0.972] |
| `dpi100` | 95/100 | 95.0% | **+1.0** | [0.888, 0.978] |

**已测结论**：五组 CI 全部与对照组重叠，**在 `page_integrity` 这一指标上
没有统计上显著的衰减**。`dpi100` 甚至高于对照 1 个百分点——
这是 n=100 的噪声，**不要解读成「低分辨率更好」**。

趋势上 `rot2` 与 `photocopy` 掉得最多（−7、−6），与直觉一致，
但以现在的样本量说不出「显著」。要得到可用的衰减曲线，
每组至少要到 300–500 条断言。

**这一指标可能不敏感**：`page_integrity` 判的是「这段文字在不在输出里」，
图像质量下降时模型仍可能读出大部分文字。金额精确到分、跨页表格行对齐
才是扫描质量真正打击的地方——那些数字要等人工核对完 `amount` 类草稿。

### 真正值得注意的是这个：2° 旋转触发复读退化

`rot2/a_share_interim_old_688515_p178`：**三次独立调用全部
`finish_reason=length`，completion_tokens 全部打满 32,768**，
输出是空的 markdown 表格行 `| | | |` 一直重复到耗尽预算。

这是本项目第二次观察到复读退化：

| # | 触发条件 | 样本 | 重试 |
|---|---|---|---|
| 1 | 纯数字信号电平表（olmOCR-Bench） | 120 页中 1 页 | 3 次全失败 |
| 2 | **财报页 + 2° 旋转** | 210 次扰动调用中 1 次 | 3 次全失败 |

**2° 是很轻微的歪斜**，扫描走纸偏一点就有。两次都是确定性失败——
重试救不回来，且都发生在密集表格上。

**对生产的含义**（工作假设，样本量不足以给频率）：
这类失败会烧掉 98,304 个 completion token，返回一页垃圾，
而且**如果走厂商 SDK，`finish_reason` 会被丢弃**，这页会被当成「解析质量差」
计入指标，而不是「调用失败」需要人工介入。裸 HTTP 才能把它抓出来
（CLAUDE.md 工程约定 1 的实证）。
