## 发现 1：表格是二元的——要么识别成表，要么整张拍平成散文

`table_tests` 的 40 页里，只有 **26 页**输出了 HTML `<table>`，**14 页一张表都没有**。
两组的 cell 断言通过率差了一个数量级：

| 该页是否产出 `<table>` | 页数 | table 断言 | 通过率 |
|---|---|---|---|
| 是 | 26 | 115/127 | **90.6%** |
| 否 | 14 | 5/60 | **8.3%** |

失败的主要形态**不是单元格取错值**，而是 `No tables found in the content`——
表格结构整个没被识别，单元格被线性化拼进正文。例如
`tables/105e91a0c9e26af4bb6fc23e13067d596a81_pg1_pg1.pdf` 输出成一行散文：
`Catalog Number UPC Number Size (EOM) Qty. Case Qty. Weight (Each) SS...`

**对金融文档的意义**（工作假设，待第三层验证）：
识别成表时单元格准确率相当高（90.6%），风险集中在「识别不出表」这个二元失败上。
这类失败对下游极其危险——输出看着像正常文本，不报错，
但报表数字已经串行拼接，行列关系全丢。
第三层必须专门统计这个「拍平率」，并区分它与「取值错误」。

**样本量注意**：14 页拍平只是 40 页里的观察，比例本身 CI 很宽，
且 olmOCR-Bench 的表格不是金融报表。这里只立现象，不给金融场景的比例。

## 发现 2：数字表格上会复读退化，烧满 32k token

120 页里 1 页失败：`tables/7d3aedd0e1d18d0e6d96bcaafea3215bd835_pg8_pg1.pdf`。
**三次独立调用全部相同**：`finish_reason=length`，`completion_tokens=32768`（打满上限）。

输出内容是把数字 `-88.4` 一直重复到耗尽 token 预算——典型的复读退化，
发生在一张纯数字的信号电平表上。

**意义**：
- 失败率 1/120 = 0.8%，但这是**确定性**失败——重试三次都一样，重试救不回来
- 触发条件是密集数字表格，**正是金融文档的常态**
- 成本上，一页失败烧掉 3 × 32,768 = 98,304 个 completion token
- runner 必须把 `finish_reason=length` 计为失败（T0 §8）。走厂商 SDK 会把这半截
  垃圾静默写进结果文件，在指标上表现为「解析质量差」而不是「调用失败」

## 发现 3：LaTeX 反斜杠双写，公式类几乎全灭

`arxiv_math` **0/30**，而 `old_scans_math` 73.3%。差异不是能力差异，是转义 bug：
doc2md 输出把 `\mathbb{N}` 写成 `\\mathbb{N}`，KaTeX 渲染直接报错
（`Got function '\\' with no arguments as subscript`）。
`old_scans_math` 的公式多为简单排版，不含反斜杠命令，所以没被波及。

诊断口径（把双写归一为单写后重判 602 条）：**通过 389 → 422**，+33 条、+5.5 个百分点。

两个数字必须并列报：产品口径是用户真实拿到的，诊断口径说明这一个 bug 的代价。
**不要用诊断数字替代产品数字。**

金融文档公式少，这条对本项目的直接影响有限，但它说明一件事：
**输出层存在未被厂商发现的低级 bug**，且 SDK 的后处理不修。

## 发现 4：doc2md 保留页眉页脚，与 doc2json→md 路径相反

`headers_footers` 的 49 条 `absent` 断言只通过 15 条——页眉页脚文本**出现在**输出里。

跑之前的预判是「md 默认丢弃页眉页脚，天然高分」，**实测推翻了**。
复核 SDK 源码后确认丢弃发生在 `doc2json → convert_json_to_markdown` 那条路径上
（`keep_header_footer=False`），而 doc2md 不做任何过滤。详见方法文档的口径陷阱 §1。

**报告动作**：凡涉及页眉页脚、脚注归属的结论都要标明走哪条路径。
两条路径对同一页给出不同 markdown，这本身是产品行为，不是我们的实现差异。

## 服务档（并发 2，全部数字附此条件）

| 项 | 值 |
|---|---|
| 墙钟 | 62.4 分钟 / 120 页 |
| 吞吐 | **1.92 页/分** |
| 单页延迟 min / 中位 / P95 / max | 5.4 / **42.2** / 173.1 / 316.6s |
| prompt tokens | 1,132,357（均值 9,436/页） |
| completion tokens | 149,878（均值 1,248/页） |

- 吞吐 1.92 页/分与 T0 §10 在并发 1/2/4/8 下实测的 1.6–1.8 页/分一致，
  **再次印证吞吐不随并发上升**
- P95 是中位数的 4.1 倍，长尾很重。长尾页对应大尺寸图像与复读退化
- 均值 9,436 prompt tokens/页，高于 T0 单页样本的 3,733——
  图像 token 由像素数决定，olmOCR-Bench 的页面尺寸比那一页大。
  **谈计费时要按页面尺寸分布给区间，不能用单页数字**
