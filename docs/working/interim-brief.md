## 已测结论

### 1. 端点不提供置信度，且不告诉你

`logprobs: true` 返回 **200 不报错**，但响应里 `logprobs` 为 `null`——**静默忽略**。
端点也无 `confidence` 字段。
`seed` 同样被接受但无法证明生效。

**影响**：research-plan §4.2 的置信度校准走不了 logprobs 这条路。
而「99.7% 自动化率」这类厂商 ROI 假设，本来要靠置信度校准数据来检验。
剩下的路只有要求厂商在 API 层暴露 confidence，或自建代理指标，成本需重新评估。

证据：`probe_out/04_page_logprobs_raw.json`、`docs/working/t0-findings.md` §7

### 2. 并发无效，吞吐还会随时段波动 2–3 倍

并发 1 → 8，吞吐恒定 **1.6–1.8 页/分**，单请求延迟近似线性增长；
并发 20 时 19 个请求卡到 300s 超时，**无 429、无 `retry-after`，是静默排队**。

不同日期同样并发下实测吞吐：**1.92 / 3.66 / 4.51 / 5.41 / 5.64 页/分**。

**影响**：声明的「并发上限 16」在吞吐上没有意义；
任何延迟或吞吐数字必须标注测量时间，单次测量不能做容量规划。
这是要求厂商提供生产环境 SLA 的直接理由。

证据：`probe_out/08b_concurrency_ladder.json`、各 run 的 `run_summary.json`

### 3. 自建金融场景集首轮指标（210 页，53 份公开披露文档）

| 指标 | n | 通过率 | 95% CI |
|---|---|---|---|
| `amount` 金额存在性与出现次数 | 562 | **97.9%** | [0.963, 0.988] |
| `unit_currency` 单位币种表头保留 | 111 | **95.5%** | [0.899, 0.981] |
| `page_integrity` 漏页与幻觉 | 480 | **91.0%** | [0.881, 0.933] |
| 内容覆盖率（输出文字数 / 文本层文字数） | 205 页 | 中位 **0.98**，P10 0.94 | — |

**210/210 页调用全部成功**，无截断、无复读。没有整页丢失，损失是局部的。

**这些数字不能单独解读**：选页刻意偏向财务报表页，绝对分数天然低于厂商在通用文档上
报的数字；且**没有基线**，91% 是好是坏取决于 Azure DI 在同一批页上是多少。

证据：`runs/inf-mllm_doc2md_20260921T013924Z/results.csv`、`docs/working/corpus-results-partial.md`

### 4. 泄漏对照：在现有指标上未观察到

同族同季节、相差一年的两组（发布日 2026-06-08 之后 vs 之前）：

| 族 | 发布日后 | 发布日前 |
|---|---|---|
| A股临时公告 | 100.0% (41) | 89.2% (37) |
| 港股中报 | 95.8% (48) | 87.5% (48) |
| A股中报 | 91.7% (12) | 85.2% (27) |
| 港股招股书 | 90.7% (43) | 92.3% (39) |
| 港股年报 | 83.7% (43) | 89.7% (39) |
| 港股 KYC | 95.8% (24) | 100.0% (15) |

六族中三族反而是新文档更高，CI 全部重叠。

**结论只能写到这里**：在 `page_integrity` 这一指标上未观察到泄漏证据；
**样本量不足以排除泄漏，也不足以确认其不存在**。该指标相对容易，
泄漏更可能体现在金额精确性与跨页表格上——那些数字尚未产出。

### 5. 扫描质量衰减不显著，但 2° 旋转触发了确定性失败

42 页 × 5 种扰动，对照组 94.0%：
`dpi100` +1.0、`jpeg30` −1.0、`dpi150` −2.0、`photocopy` −6.0、`rot2` −7.0，
**CI 全部与对照重叠，无统计显著衰减**。

但 `rot2` 组出现一次**复读退化**：财报页旋转 2°，三次调用全部
`finish_reason=length`、打满 32,768 token，输出为空表格行无限重复。

这是本项目第二次观察到该模式（另一次在纯数字表格上），
**两次都是重试三次全失败的确定性失败，都发生在密集表格上**。
一次烧掉 98,304 个 completion token 并返回一页垃圾。

**关键**：走厂商 SDK 时 `finish_reason` 会被丢弃，这页会被计成「解析质量差」
而不是「调用失败需人工介入」。裸 HTTP 才抓得出来。

### 6. 输出非确定性：逐字一致 99.0%，断言结论翻转 0.17%

210 页 × 3 次、`temperature: 0`：

| 层次 | 结果 |
|---|---|
| 逐字一致 | 208/210 = **99.0%** |
| 断言结论翻转 | 2/1153 = **0.17%**，CI [0.0005, 0.0063] |
| 其中 `amount` 类 | 562 条 **零翻转** |

两条翻转的根因：全角 `（2）` 与半角 `(2)` 在不同次调用间摇摆；
表格 `colspan` 重组使「单位：元」出现次数由 2 变 1，勾选框由
`☑适用 ☐不适用` 变成 `是/否` 两个单元格。

**不稳定不是随机字符噪声，是版面结构解释的摇摆**，恰好落在金融文档最敏感处。
金额本身是稳定的。

**0.17% 是否可接受，需与 Azure DI 比较后由业务方判断**——
流水线式 OCR 是确定性的，同输入必然同输出。本报告不替业务方下这个判断。

### 7. 端点只挂一个模型，档位与版本号不可知

`/v1/models` 返回 404。八个模型名探测中只有 `inf-mllm` 与空串返回 200，
`inf-mllm-pro`、`Infinity-Parser2-Pro` 等全部 404。

**无法确认测的是 Pro 还是 Flash，也无法锁定版本**。
厂商可随时更换后端模型而不通知，届时所有数字失效。

## 方法透明度

**报告的说服力不来自分数高低，来自评测过程的独立性可被验证。**
以下是评测过程中我们自己犯过并修正的错误，全部记录在案：

| 错误 | 后果 | 修正 |
|---|---|---|
| 禁止串是目标值的前缀（`100,000` → `100,00`） | `amount` 通过率假性显示 **9.9%**，真实值 97.9%，差 88 个百分点 | 禁止串须非子串，逐个校验 |
| `exactly_once` 用于会重复出现的金额 | 564 条中 134 条注定假失败 | 改 `exactly_n`，期望次数由文本层决定 |
| 页锚点混入纯数字行 | 8 条假失败 | 要求锚点含 ≥8 个文字字符 |
| 覆盖率直接比字符数 | 被 HTML 表格标记撑大，得出中位 1.82 的假象 | 剥标记后只数文字与数字 |
| 目录页点线计入字符数 | 得出 0.18 的假性「漏读」 | 同上 |
| 中文「单位」当成计量单位 | 抓到「单位：<公司名>」，162 条多数报废 | 收紧正则，剩 111 条 |
| HKEX 日期参数写错 | 新旧两个时间窗口取到同一批文档 | 必须用 `fromDate`/`toDate` |
| HKEX 未翻页 | 老窗口假性 0 命中 | 按 `rowRange` 翻页 |
| 表格内折行的金额只抽到前半段（`181,801,7`/`31.11` → `181,801`） | 37 条金额断言目标值被截断，成了「前缀匹配必过」的空心测试。**通过率数字恰好没变，但测的东西是错的** | 行尾为「逗号+1~2 位」即判定折行并拼接；拼接后仍不完整的宁可不出 |

**每一处都会让数字失真，或让数字看起来对而测的东西是错的。** 其中第一处若未查证就写进报告，
结论会变成「该产品金额识别能力极差」，而真相是判定器写错了。
**异常值必须查到底再报，无论它对谁有利。**
