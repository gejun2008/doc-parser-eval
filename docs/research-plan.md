# INF TECH 文档解析 API 评测计划（v2 · API-only）

> **本版取代 2026-09-14 的「Unlimited-OCR + GCP 自建」计划。**
> 评估对象已变更：不是百度开源的 Unlimited-OCR，而是 **INF TECH（无限光年）** 的
> FinIE 平台与 **Infinity-Parser2** 文档解析产品，通过其提供的测试 API 评测。
> 原计划中 GCP 部署、GPU 配额、显存边界、依赖冲突等章节全部作废。
>
> 边界条件（2026-09-15 确认）：**不自建，只测 API** ｜ 读者为技术主管与团队内部 ｜
> 只能用公开金融文档 ｜ 交付周期 2–3 周 ｜ **本轮聚焦 OCR / 文档解析（Parse）**。

---

## 0. 一句话目标

用我们自己的数据和指标，测出 Infinity-Parser2 在 HSBC 金融文档场景下的真实能力边界，
产出一份能支撑「在哪些文档类型上可用、在哪些不可用、POC 该怎么划范围」的技术评估报告。

**报告的说服力不来自分数高低，来自评测过程的独立性可被验证。**
每一个数字都必须能追溯到：谁产生的、用什么数据、什么口径。

## 1. 评估对象与已核实事实

### 1.1 产品线

| 对象 | 说明 | 本轮 |
|---|---|---|
| **Infinity-Parser2** | 旗舰解析引擎。站点宣称金融文档整体字符准确率 **93.56%** | **主测对象** |
| **PDFParser** | 站点定位「最低延迟、适合实时场景」，大概率非同一模型 | 同厂商内部对照，必测 |
| FinIE 平台 Extract 模式 | 结构化抽取 | 次要，时间允许才做 |
| FinIE 平台 Chat 模式 | 对话式查询 | **本轮不做** |

### 1.2 已核实的技术事实（来源：技术报告 / HF 模型卡）

- **开源权重，Apache 2.0**。Pro 与 Flash 均在 Hugging Face 公开
  （`infly/Infinity-Parser2-Pro`、`infly/Infinity-Parser2-Flash`）
- **Pro**：基座 Qwen3.5-35B-A3B（MoE），BF16 约 70GB
- **Flash**：基座 Qwen3.5-2B；宣称相对 Infinity-Parser-7B 吞吐提升 3.68×（441 → 1,624 tok/s）
- 发布时间 **2026-06-08**
- 训练语料 Infinity-Doc2-5M，中英双语，文档类型清单中**明确包含 financial reports**
- 推理支持 Transformers / vLLM / SGLang / Docker，另有 `infinity_parser2` Python 库
- **厂商自陈缺陷**：多模态指令跟随能力欠佳；**不保留粗体、斜体、删除线等细粒度格式**；
  多语种（中英之外）性能下降

### 1.3 厂商自报数字的三套口径（关键）

| 出处 | 数字 | 指标口径 |
|---|---|---|
| FinIE 网站首页 | **93.56%** | 金融文档「整体字符准确率」 |
| 技术报告 / HF | **87.6%** | olmOCR-Bench（pass-fail 单元测试） |
| 技术报告 | **74.3%** | ParseBench |
| 技术报告 | 94.76% | PubTabNet 表格 TEDS |
| 技术报告 | 97.7% | UniMERNet 公式 CDM |
| 技术报告 | 96.43 / 61.89 | DocVQA / MMMU |

**同一模型，93.56% 与 74.3% 并存。** 对外网站挂的是最高且指标最宽松的那个。
字符准确率天然虚高——金融文档绝大多数字符是易识别正文，真正要命的金额、账号、
跨页表格行在字符准确率里被稀释成小数点后的噪声。

**报告动作**：把这三个数字并列成一张表放进正文。不加评论，数字自己说话。

### 1.4 厂商同时控制了对比场与 ROI 模型

FinIE 站点自带「竞品擂台」与「ROI 评估」两个模块：

- 擂台对手：DeepSeek-OCR-2、MinerU2.5、PaddleOCR-VL-1.5、Qwen3.5-35B-A3B、Gemini3.1-Pro。
  **其中 Qwen3.5-35B-A3B 正是 Infinity-Parser2-Pro 自己的基座模型**——
  作为消融实验合理，摆在「竞品」位置上有误导性，报告需点出
- ROI 输出：年节省 ¥1,598,000、自动化率 99.7%、处理时长 4 小时 → 2 分钟（均为模拟值）。
  参数为年文档量 V、自动化率 a_old/a_new、处理时长 t_old/t_new、人工时薪 w
- 技术报告标注「带 * 的基线分数由我们重新评测」——**自跑对手分数**，需核对

**报告动作**：不去驳 ROI 模型，而是**拆开它的假设逐条代入 HSBC 参数重算**，
给出「在什么条件下 ROI 成立 / 不成立」的曲线。99.7% 自动化率在银行场景下不可能成立，
因为关键字段必须人工复核——这一点用我们自己测出的置信度校准数据来证明，而不是断言。

## 2. 三个贯穿全局的核心判断

### 2.1 训练集泄漏是本次评测最大的结构性威胁，必须量化而非回避

训练语料明确含 financial reports，而我们只能用公开金融文档。公开年报几乎必然在训练集里。

**唯一有效对策是时间切分**：模型发布于 2026-06-08，
因此评测主力用 **2026 年 6 月之后新披露**的年报、中报、临时公告——训练时不存在。

同时保留一组 6 月前的老文档作对照，**报告「6月前 vs 6月后」两组分数**。
若新文档上明显掉分，泄漏就被量化了，这是全报告最硬的一张牌。
若没掉分，则泄漏担忧被排除，结论同样有价值。

### 2.2 公开 benchmark 只是准入门槛，决定性证据在自建金融场景集

olmOCR-Bench 和 ParseBench 都是单页通用文档评测，与 HSBC 场景相关性弱。
它们的作用是证明「我们复现得出来、没冤枉厂商、能同口径对比」。

**真正决定结论的是第三层自建集，按文档类型分层出数。**
决策是按场景走的——「年报表格抽取可用、低质扫描 KYC 件不可用、建议 POC 限定在 X」
对技术主管有用；「整体 87 分」没用。**分层表是正文主体，不是附录。**

### 2.3 学术指标撑不起决策，指标必须对齐业务后果

编辑距离、TEDS 对「要不要上」这个问题没有解释力。
正文指标必须是字段级准确率与错误后果分级；学术指标放附录，仅用于与厂商数字对齐口径。

## 3. 数据集设计（三层）

### 3.1 第一层：厂商数据集复现

用厂商提供的测试数据集与结果，**同口径复现**，回答一个问题：他们报的数能不能跑出来。

- 复现不出来 → 这本身是全报告最有力的一条发现
- 复现得出来 → 才有资格谈后面两层

同时**审查数据集本身**，这块常比跑分更有产出：

- 样本的文档类型分布、页数分布、电子版 vs 扫描件比例、中英文比例、难度分布
- **人工抽检 50 条标注，算出厂商 GT 自身的错误率**。
  若 GT 错误率有 3–5%，他们报的 93.56% 就失去了分辨率——这一句的杀伤力胜过十组自测数据

### 3.2 第二层：中立公开基准（准入门槛）

- **OmniDocBench v1.6 的金融/财报切片**，不跑全量（API 调用有成本与限流，全量不划算）
- 指标：文本编辑距离、表格 TEDS、公式 CDM、阅读顺序编辑距离——与厂商口径对齐
- olmOCR-Bench 抽样子集，仅用于校验厂商自报的 87.6%，时间紧可砍

### 3.3 第三层：自建金融场景集（决定性证据）

**全部来自公开渠道**，可公开引用、可复用为回归集。目标 200–300 页、约 200 条断言。

| # | 文档族 | 来源 | 页数 | 对应 HSBC 场景 |
|---|---|---|---|---|
| 1 | A股年报/中报（2026H1） | 巨潮资讯网 | 40–60 | 企业授信、财务分析 |
| 2 | 港股年报/中报（繁体+英文） | HKEX 披露易 | 40–60 | 跨境企业客户、中英混排 |
| 3 | 临时公告（含表格） | 巨潮 / HKEX | 30–40 | 事件监控、风险预警 |
| 4 | 招股书 / 上市文件 | HKEX | 30–40 | 承销尽调、长文档 |
| 5 | 评级与研究报告（公开版） | 评级机构官网 | 20–30 | 信用分析 |
| 6 | 贸易金融单据（LC / 提单 / 商业发票模板） | ICC / 银行公开样本 | 20–30 | 贸易融资 |
| 7 | KYC 类（章程、董事名册、股权披露） | HKEX 披露易 | 20–30 | 客户尽调 |
| 8 | **低质扫描扰动组** | 由 1–7 派生 | 30–40 | 传真件、多代影印件 |

**时间切分**：1–5 类**优先取 2026-06-08 之后披露**的文档；
另设一组 2025 年的老文档作泄漏对照。

**扰动组生成方式**（零标注成本，复用第 1–7 类的断言）：
重新打印扫描、降分辨率至 150/100 DPI、JPEG 高压缩、轻微旋转 ±2°、加高斯噪声。
真实银行文档大量是传真与多代影印件，**这一组的衰减幅度比原始分数更接近生产表现**。

### 3.4 标注策略：只做断言，不做全文标注

全文 markdown GT 每份要数人日，会拖死整个评测，而且会把评测稀释成又一次单页 OCR 测试。

借 olmOCR-bench 的 pass/fail 思路，每份文档 10–20 条可自动判定的断言，共约 200 条。
**标注工作量控制在 2–3 人日。**

断言七类：

1. **金额/数字精确性**：「营业收入 1,234,567,890 元应恰好出现一次，且不得出现 1,234,567,89」
2. **单位与币种**：「表头标注『人民币千元』须保留，金额不得被换算或丢失单位」
3. **跨页表格合并**：「合并资产负债表跨第 7–9 页，合并后应为 42 行」
4. **跨页阅读顺序**：「第 18 页续表行须挂在第 17 页的表头下」
5. **漏页 / 幻觉**：「第 12 页锚点串须出现」「不得出现原文不存在的科目名」
6. **页眉页脚与脚注归属**：「第 12 页脚注不应混入正文流」
7. **格式保留**：「附注中加粗的『重大』二字须保留强调标记」
   （针对厂商自陈的 bold/italic/strikethrough 缺失）

**零成本自动检查**：公开年报 PDF 自带文本层，用 pymupdf 抽出作文本级参考。
它不能当阅读顺序 GT（文本层顺序常错），但每页取唯一锚点串检查是否全在、
有无凭空多出，对漏页与幻觉检测非常好使，且完全自动。

## 4. 指标体系

### 4.1 正文档（决定结论）

**字段级准确率**——按字段类型分别统计，不合成总分：
金额、日期、账号/代码、主体名称、币种、单位（千元/百万元）。
金融文档里单位错一档等于金额错三个数量级。

**错误后果分级**，主推 critical error rate：

| 等级 | 定义 | 例 |
|---|---|---|
| **Critical** | 直接导致业务错误决策 | 金额漏位/错位、账号错、日期错、单位误判、币种错 |
| **Major** | 需人工返工 | 跨页表格合并错、行错位、附注归属错、漏页 |
| **Minor** | 不影响使用 | 格式、标点、空格、换行 |

一个 critical 错误在银行的代价不等于十个 minor。报告不报加权总分。

**跨页表格合并正确率**——金融文档的核心难点，单列。

**幻觉率**——输出了原文不存在的内容。所有 LLM 类解析产品的共同软肋，必测。

**格式保留率**——粗体/斜体/删除线。厂商已自陈缺失，低成本验证其业务影响。

### 4.2 可靠性档（银行场景特有，也是最容易被别人漏掉的一块）

**置信度校准**——把 API 返回的 confidence 分箱，画 confidence vs 实际准确率曲线。
**若曲线是平的，说明置信度不能用于分流人工复核，自动化率上不去，ROI 直接塌一半。**
这是全报告技术含量最高的一页，也是驳倒厂商 99.7% 自动化率宣称的唯一严谨方式。

**静默失败率**——输出看起来完全合理但内容错误，且系统无任何提示。
银行场景里最危险的一类。定义为：critical 错误中 confidence 高于中位数的占比。

**重复调用一致性**——同一份文档连调 3 次，输出是否逐字一致。
非确定性在可审计场景是硬伤，很多人不测，但审计与风控一定会问。

**失败与超时率**——大文档、复杂版式下的 API 硬失败比例。

### 4.3 服务档

- 延迟 P50/P95，按页数分档（1 页 / 5 页 / 30 页 / 100+ 页）
- 并发能力与速率限制（测试 API 的限流值本身要记录下来并在报告中声明，
  因为它会影响所有延迟数字的可比性）
- 计费口径：按页 / 按 token / 按调用，与 Azure DI 的 $0.01/页 能否同口径对比

### 4.4 附录档

学术指标（编辑距离、TEDS、CDM、阅读顺序 EDS），仅用于与厂商自报数字对齐口径。

### 4.5 统计严谨性（内部技术评审会挑这个）

- 每个分层标出 **n 与置信区间**
- 200 样本上的 87% vs 89% 不显著，不得称「更好」
- 样本量不足的分层明确写「样本不足，不下结论」
- **主动标注不确定性会提高可信度，不是削弱它**

## 5. 对照基线

没有基线的绝对分数不可解释。报告的核心句式是「相对现状提升/下降多少」。

| 基线 | 优先级 | 说明 |
|---|---|---|
| **Azure DI (Layout)** | **必保** | 现状方案，「换不换」的真正对手。$10/1000 页无阶梯折扣。走 API 无需 GPU |
| **PDFParser** | **必保** | 同厂商内部对照，验证「低延迟模式」代价几何 |
| **Gemini-3-Pro 或 GPT-5.4** | 保留 | 能力上限参照。走 API，边际成本低。若闭源大模型在跨页表格上赢了专用模型，结论就是「别买专用的」——这也是有价值的结论 |
| 厂商自报数字 | — | 是被验证对象，不算基线 |

**同口径陷阱（必须提前声明）**：Azure DI 输出自有 JSON，需转换为可比格式。
**转换规则必须在附录公开**，否则等于栽赃对手，这个漏洞评审一眼看得出来。
Gemini / GPT 直接要求输出 markdown，无需转换。

## 7. 报告结构（读者：技术主管与团队内部）

Markdown 为本体，需要时一条命令导出 docx。正文 10 页内，结论先行。

1. **摘要（1 页）**——在哪些文档类型上可用 / 不可用 / POC 建议范围，配三个关键数字
2. **厂商声明核验**——三套口径对照表、数据集审查结果、GT 错误率、复现结论
3. **能力验证（正文主体）**——**按文档族分层的准确率表**、critical error 分布、
   跨页表格、幻觉率、格式保留
4. **可靠性**——置信度校准曲线、静默失败率、重复一致性。
   这一节直接回应厂商的 99.7% 自动化率宣称
5. **泄漏与鲁棒性**——6月前/后对照、扰动衰减曲线
6. **对照与成本**——相对 Azure DI 的提升/下降、参数化 ROI 重算
7. **工程现实**——限流、超时、版本管理、格式缺失等不体现在分数里但决定落地难度的东西
8. **风险与未决**——见下节
9. **附录**——方法论、断言清单、Azure 转换规则、数据集构成与来源 URL、
   API 调用参数、**调用时间戳与模型版本号**、原始输出留存位置

**可复现性是说服技术评审的核心**：任何人拿附录能重跑一遍。

**结论形态**：不写「推荐 / 不推荐」，写
「在 X 类文档上可替代现状（证据：…），在 Y 类上不可（证据：…），
建议 POC 范围限定为 Z，退出标准为 …」。
**诚实列出 Inf 赢的地方和输的地方——全是正面的评测报告在银行里没人信。**
