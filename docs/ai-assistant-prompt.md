# 给公司电脑上 AI 助手的起始 prompt

在公司电脑上用 Copilot / GPT 等助手接手本项目时，**把下面整段粘贴进去**作为第一条消息。
它把口径纪律写死，避免助手在不了解背景的情况下把数字写错方向。

---

## 复制以下内容

```
你要接手一个已经进行到一半的技术评测项目，把它写成报告。先读这四份文件，
不要跳过：

  README.md                   项目概览与当前状态
  docs/report-outline.md      报告逐节对照表——每节用哪些数据文件、还缺什么
  docs/interim-brief.md       中期简报，已有结论都在这里
  docs/azure-di-baseline.md   我接下来要跑的基线，以及必须声明的不对称

项目背景：评测厂商 Infinity-Parser2 文档解析 API，判断能否替代现状方案
Azure Document Intelligence。读者是技术主管与团队，不是销售材料。

**这份报告的说服力不来自分数高低，来自评测过程的独立性可被验证。**
每个数字都要能追溯到具体文件、调用时间戳和模型版本号。

## 五条硬纪律，任何情况下不得违反

1. **不合成加权总分。** 按文档族、按断言类型分层出数。
   compare_systems.py 输出里「全部」那一行不是总分，只是同口径汇总。

2. **p ≥ 0.05 写「未观察到显著差异」**，不得写成「持平」「相当」「不相上下」
   「基本一致」。两边判的是同一批断言，属配对数据，用的是 McNemar 检验，
   看的是 b（只有 A 对）与 c（只有 B 对）的条数差。

3. **n < 30 的分层写「样本不足，不下结论」**，不要为了表格好看而合并分层。

4. **异常值必须查到底再报。** 本项目出现过一次判定器 bug，让金额通过率
   假性显示 9.9%，真实值 97.9%，差 88 个百分点。数字高得反常同样要查——
   错误不会只朝一个方向。查的办法：打开 runs/<run_id>/results.csv 看
   why 列，再打开对应的 raw/*.json 看模型实际输出了什么。

5. **对自己结论不利的因素要主动写出来。** 例如：Azure DI 按整份文档分析，
   即使指定单页也可能利用全文上下文，而被测方是逐页独立调用——
   这一条对 Azure 有利，必须写进报告。完整的四条不对称见
   docs/azure-di-baseline.md。

## 结论形态

**不要写「推荐 / 不推荐」。** 写成：
  「X 类文档可替代现状（证据：…）」
  「Y 类不可（证据：…）」
  「POC 范围建议 Z」
  「退出标准：…」

诚实列出被测方赢的地方和输的地方。全是正面的评测报告在银行里没人信。

## 已知的、必须在报告里声明的缺口

- 贸易融资单证未覆盖——找不到合规公开源，五类来源的排除过程见
  docs/corpus-method.md。该场景与已测文档族结构差异大，**现有结论不可外推**
- critical error rate 依赖 136 条人工核对，未做完则该指标为空，
  不要用其他指标替代它
- 置信度校准做不了——端点不返回 logprobs 且静默忽略该参数
- 被测模型的档位与版本号未知，厂商未答复，报告须标注此限制
- 每族每窗口仅 4 份文档，多数分层样本不足

## 现在要做的事

1. 按 docs/azure-di-baseline.md 跑 Azure DI 基线（两层，约 $3.30）
2. 跑 tools/compare_systems.py 得到分层对照表
3. 按 docs/report-outline.md 逐节成文，正文 10 页内，结论先行
4. 成文前对照 report-outline.md 末尾的九条自检清单

先告诉我你读完那四份文件后的理解，以及你认为现在最缺的是什么，
再开始动手。
```

---

## 为什么要这样写

- **先读文件再动手**：助手容易凭常识补全背景，而本项目的很多结论是反直觉的
  （例如扰动组里低分辨率反而略高、页眉页脚在两条产品路径上行为相反）
- **把纪律写在前面**：统计口径一旦写错方向，整份报告的结论会反过来
- **举 9.8% 那个例子**：让助手知道「反常的数字要查，不要直接写进报告」
  不是空话，这个项目真的发生过
- **明确要求先复述理解**：先确认它读懂了，再让它动手，比事后返工便宜
