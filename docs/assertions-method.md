# 断言生成与人工核对：分层口径

schema 见 `docs/assertions.md`。本文件记的是**实际实现的分层**：
哪些断言机器就能验、哪些必须人眼过、以及为什么这么分。

## 核心区分

PDF 文本层对「**这串字符在不在这一页**」是可靠的——字符本来就来自它。
它不可靠的是**顺序**和**归属**：跨列拼接、两栏数字连在一起、行标签配错。

所以按「机器能不能验」分层，而不是按断言类型分层。

| status | 条数 | GT 来源 | 验什么 | 不验什么 |
|---|---|---|---|---|
| `auto` | 480 | 文本层唯一锚点 | 漏页、幻觉 | — |
| `auto_textlayer` | 675 | 文本层 | 金额/单位**存在性与出现次数** | **科目归属** |
| `draft` → 人工 | 81 | 人工 | 金额与科目**是否同行** | — |

`auto_textlayer` 细分：`amount` 564 条、`unit_currency` 111 条。

**人工只需处理 81 条归属断言 + 60 条审计抽样 = 141 条**，
不是最初估计的 726 条。

## 为什么归属必须人工

现有的 `amount` 断言只判「这串数字在不在输出里、出现几次」。
**数字出现在错误的行里照样算通过**——而那正是金融文档最要命的失败方式：
「应收账款 1,234,567」变成「应付账款 1,234,567」，金额没错，科目错了。

`amount_label` 类用 `label_proximity` 规则：金额与其行标签在输出中的
字符间距须 ≤ 120（空白归一后）。这条断言的 GT 必须人工确认，
因为**文本层的行首标签本身可能就是错的**——跨列拼接会把隔壁列的标签配过来。
脚本生成的 label 只是候选，人眼对着渲染页确认后才能用。

## 审计抽样

`auto_textlayer` 的 GT 来自文本层而非人工，它也可能错。
抽 60 条进审核页（固定 seed 20260921，可复现），人工复核后给出
**文本层 GT 的错误率上界**，写进报告。

没有这个抽样，「自动生成 675 条断言」这句话在评审面前站不住。

```bash
python tools/review_assertions.py --audit 60
```

## 两个自己犯的错（都会让数字严重失真）

### 1. 禁止串是目标值的子串 → 通过率假性跌到 9.9%

第一版 `forbid_forms()` 把「少末位」当作错误形态：
`100,000` → `100,00`。但 `100,00` 是 `100,000` 的**前缀**——
只要正确金额出现，这个禁止串必然也在，于是必然判失败。

564 条 `amount` 里 **500 条**因此被判假失败，通过率显示为 **9.9%**。
修正后（禁止串必须不是目标的子串）是 **97.9%**。

差了 88 个百分点。**如果没查这个异常值就写进报告，整份报告就废了。**
现在 `forbid_forms()` 只保留结构上不可能是子串的形态：丢掉全部千分位分隔符、
小数点左移一位，并在返回前逐个校验。

### 2. `exactly_once` 用在会重复出现的目标上

报表里同一金额在本期/上期两栏出现是**正常的**。
第一版一律用 `exactly_once`，564 条里 134 条注定假失败。
现在改用 `exactly_n`，期望次数由文本层实际出现次数决定。

同类问题还出现在 `page_integrity` 上：锚点混进纯数字行，
8 条因同一金额出现两次而假失败。已改为要求锚点含 ≥8 个文字字符。

### 3. 中文「单位」不只是计量单位

`unit_currency` 第一版正则匹配 `单位[：:]...`，抓到了
「单位：海目星激光科技集团股份有限公司」——那个「单位」是**公司**。
又因为匹配裸 `元` / `RMB`，抓到 39 条 `'元'`、37 条 `'RMB'`，一页里到处都是。

162 条里绝大多数是废的。现在要求必须带计量语境
（`单位：元 币种：人民币`、`RMB'000`、`HK$'000`），剩 111 条有效。

## 教训

**异常值必须查到底再报。** 9.9% 这个数字如果直接进报告，
结论会变成「该产品金额识别能力极差」，而真相是判定器写错了。
反过来，如果某个数字高得反常，同样要查——错误不会只朝一个方向。

## 人工审核怎么做（公司电脑上）

**不需要起服务器。** 审核页是自包含 HTML，页面图以 base64 内嵌，
双击用浏览器打开即可。

```bash
python tools/review_assertions.py --audit 60      # 生成 review/，约 39 MB
```

打开 `review/index.html`，表里「草稿」列非 0 的才需要处理。
**53 份文档里只有 17 份有待审条目**，其余 36 份可以跳过：

| 待审条数 | 文档数 |
|---|---|
| 0 | 36 |
| 1–5 | 16 |
| 32 | 1 |

逐条看页面图确认后点「通过」或「删除」，金额抽错可直接改输入框里的值。
全部看完点 **「导出全部」**——它会把所有已审文档汇成一个 `review_all.json`，
不必逐份下载 53 次。然后：

```bash
python tools/apply_review.py ~/Downloads/review_all.json
python tools/apply_review.py --status            # 看进度
```

### 两个坑

1. **`file://` 下部分浏览器（Safari 尤其）拒绝 localStorage**。
   审核页已做容错：拒绝时退回内存态并在页面顶部显示橙色警告条——
   **看到警告条就必须当场导出，关页面即丢失**。
   稳妥做法是用 Chrome，或用本地服务打开：`python -m http.server 8765`
2. **不要混用打开方式**。`file://` 与 `http://localhost` 是不同的源，
   localStorage 不互通，中途切换会看不到之前的审核结果。

## 复现

```bash
python tools/make_assertions.py                  # 生成，已有人工结果时需 --force
python tools/review_assertions.py --audit 60     # 审核页（81 归属 + 60 审计）
python tools/apply_review.py ~/Downloads/review_*.json
python tools/apply_review.py --status            # 看进度
python tools/check.py runs/<run_id>
```
